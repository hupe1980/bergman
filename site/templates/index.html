Iceberg maintenance
without the JVM

Bergman keeps Iceberg tables healthy — compacting small files with their delete files applied, re-packing manifests, expiring snapshots and removing orphans — driven by declarative policies and built on iceberg-rust. No Spark, no Trino, no cluster. One crate, one binary, and a library any Rust service can embed.

Maintenance is a background tenant.

It must never win against a foreground writer, and never corrupt one. Every design decision below follows from that — triggers instead of schedules, replan instead of retry, and a deletion path with seven independent checks standing in front of it.

Policies declare intent

Every setting resolves through four layers: the matching rule, your defaults, the table's own Iceberg properties, then the specification default. A table already carries its owner's intent, and Bergman reads it rather than competing with it.

How layering works →

Triggered, not scheduled

A schedule decides when a table is evaluated; measurements decide whether anything runs. A table already at target file size costs a handful of metadata reads and no data I/O — which is what makes it safe to evaluate thousands of tables often.

What triggers a rewrite →

Every decision is legible

Each planned operation carries the measurement that crossed a threshold and the threshold it crossed. policy explain prints every effective value together with the layer it came from. An operation you cannot interrogate is one you cannot trust with your data.

See provenance →

Deletion is the hard part

Dry run by default. A grace period with a hard 24-hour floor that cannot be configured away. Unknown file age means too young. Segment-wise containment, and a refusal to scan a location another table lives inside. Re-verification against freshly loaded metadata, and a ceiling on the blast radius.

The safety model →

Replan, never re-commit

Losing a compare-and-swap to a foreground writer is reported as conflicted, not failed — it is the design working. Each retry reloads the table, because re-submitting a commit computed against a table that has since moved is how deleted rows come back.

The commit model →

A library first

The binary is a thin consumer of the same public API you get. No global state, no logger it installs, no runtime it creates. Planning is pure, so dry-run is not a mode to remember — it is what happens when you stop before run().

What plan shows is what run does

Both build the same plan through the same code, so a preview cannot disagree with the thing it previews. Every operation carries the measurement that triggered it and the threshold it crossed.

Policies, in one file

[[catalogs]]
name      = "prod"
uri       = "http://localhost:8181/catalog"
warehouse = "s3://lake/warehouse"
token_env = "BERGMAN_CATALOG_TOKEN"   # a name, never a value

[defaults.snapshots]
max_age     = "7d"        # omitted -> history.expire.max-snapshot-age-ms
min_to_keep = 3

# A streaming target: files are the right size, but equality deletes
# amplify every read. Trigger on the delete ratio, not on file sizes.
[[rules]]
match    = "prod.streaming.events_*"
schedule = "0 */2 * * *"
[rules.compaction.trigger]
delete_ratio = 0.05

[[rules]]
match = "prod.tmp.**"
skip  = true              # explicit exclusion beats implicit

Pick your shape

Cron job

One cycle, then exit. A Kubernetes CronJob, an ECS scheduled task, or a line in a crontab. Exits 2 when something needs attention, so a broken job cannot look healthy.

bergman run \
  --config /etc/bergman.toml \
  --audit-log /var/log/bergman.jsonl

Read-only first

Report health and plan work without writing anything, until the plans look right. The same code path run uses — what you were shown is what happens.

bergman inspect
bergman plan --format json \
  | jq '.tables[].operations[]'

Embedded

A Rust service holding the engine in-process — a catalog, a streaming writer, a control plane — with an observer for metrics or an approval gate.

let bergman = Bergman::builder(config)
    .with_observer(observer)
    .build()
    .await?;

let plan = bergman.plan().await?;
let report = bergman.run(&plan).await?;
